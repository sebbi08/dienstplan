# Groups (Gruppen), Step 3 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A facility can be divided into groups.
- Employees have a home group or none (Springer).
- Single duties can count for another group.
- Required duties and week templates apply to the facility or to one group.
- The plan shows the groups as side-by-side blocks with a per-day attendance count.

**Architecture:**
- A new `groups` table.
- Nullable `group_id` columns on employees, entries, coverage_rules and week_templates.
- The effective group of an entry is `entries.group_id`, otherwise `employees.group_id`.
- Coverage checking becomes group-aware.
- Snapshots carry group data, so released plans show blocks.
- With no groups, every output is unchanged.

**Tech Stack:** Nuxt 4 (Nitro), Drizzle ORM + better-sqlite3, zod, Vitest, Nuxt UI 4.

**Spec:** docs/superpowers/specs/2026-10-08-groups-design.md

## Global Constraints

- UI German, code English. Texts live in `app/locales/de.ts`. Commit messages end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- Services take `db` first, then `facilityId`. Rows of another facility answer `*_not_found` (404) and are never confirmed.
- With no groups in a facility, all DTOs except new empty fields, all warnings and all UI stay as before. Every existing test keeps passing.
- Error codes:
  - `group_name_required` (400)
  - `group_name_taken` (409)
  - `group_not_found` (404)
  - `group_has_members` (409)
- Migration `0022_groups` runs on the user's real data. It must be:
  - `CREATE TABLE groups`;
  - `ALTER TABLE … ADD group_id` on employees, entries, coverage_rules and week_templates;
  - only `week_template_marks` may be rebuilt, keeping its rows with group 0.

  Generate it with `npx drizzle-kit generate --name groups`. Hand-write it (`--custom`) if drizzle rebuilds other tables.
- Old release snapshots have no group data. Read missing values as null and show no blocks.
- The cell identity used for pending changes and notifications includes the entry's `groupId`. Missing and null are encoded the same way, so existing snapshots produce no spurious changes.
- New routes are classified in `tests/api/permissions.test.ts`. Group management is Träger-only (`requireProvider`); everything else uses `requireAdmin`.

## Review Focus

1. **Upgrade with existing data.** After the upgrade with 17 existing release snapshots, no month shows pending changes and no notification is sent on re-release. Tests: Task 2 (identity) and Task 5 (plan).
2. **Coverage on a mixed day.** On one day, a facility rule and a group rule both apply, a Springer works, and one member's duty counts for another group. Each rule must count exactly the right duties. Test: Task 3.
3. **Group from another facility.** A Leitung of facility A uses a group id of facility B: as a home group, as an entry group, in a rule, in a template, or to delete it. The answer is 404 `group_not_found`, and nothing changes. Test: Task 7.
4. **Deleting a group.** Deleting a group that still has members is refused. Deleting an empty group removes its rules and templates and clears entry groups; no entry is lost. Test: Task 1.
5. **Applying a group template.** It fills only empty cells of the group's current members. It never touches other groups, Springer, helpers or another plan's days. Test: Task 4.
